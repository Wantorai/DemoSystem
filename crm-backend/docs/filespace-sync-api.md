# FileSpace Sync API

Все запросы используют обычный JWT CRM:

```http
Authorization: Bearer <token>
```

## Первичная синхронизация

```http
GET /filespace/sync/snapshot?limit=500
```

Ответ содержит:

- `roots` — доступные пользователю личные и общие пространства;
- `items` — плоский список папок и файлов;
- `nextCursor` — курсор следующей страницы;
- `hasMore` — признак продолжения;
- `eventCursor` — позиция журнала изменений на момент начала снимка.

Для следующих страниц нужно передавать оба курсора:

```http
GET /filespace/sync/snapshot?limit=500&cursor=<nextCursor>&eventCursor=<eventCursor>
```

После последней страницы desktop-клиент сохраняет `eventCursor` и начинает получать изменения.

## Получение изменений

```http
GET /filespace/sync/changes?cursor=<eventCursor>&limit=500
```

Типы событий:

- `upsert` — создать или обновить локальную запись;
- `delete` — переместить запись в локальную корзину или убрать из синхронизируемой папки;
- `restore` — восстановить запись;
- `purge` — окончательно удалить локальную запись.

После обработки ответа клиент сохраняет `nextCursor`. Пока `hasMore=true`, следующий запрос выполняется сразу. Затем можно перейти к периодическому опросу.

`roots` возвращаются при каждом запросе. Клиент сравнивает их со своим локальным списком: так обрабатываются выдача и отзыв доступа к общим папкам.

Если `resetRequired=true`, сохранённый курсор устарел или база была восстановлена. Клиент должен заново выполнить первичную синхронизацию. По умолчанию журнал хранится 90 дней, настройка: `FILESPACE_SYNC_EVENT_RETENTION_DAYS`.

## Отправка локальных изменений

Desktop-клиент использует существующие API FileSpace:

- создание папки — `POST /filespace/folders`;
- загрузка нового файла — `POST /filespace/uploads`, затем `POST /filespace/uploads/:fileId/complete`;
- новая версия — `POST /filespace/files/:fileId/versions/initiate`, затем `POST /filespace/files/:fileId/versions/:versionId/complete`;
- переименование файла — `PATCH /filespace/files/:fileId`;
- перемещение — `POST /filespace/move`;
- удаление — `DELETE /filespace/files/:fileId`.

При загрузке новой версии передаётся `baseVersionId`. Если серверный файл уже изменился, ответ инициализации содержит `willCreateConflict=true`; загрузку всё равно нужно продолжить. После передачи содержимого сервер сохранит его отдельной конфликтной копией. HTTP `409` возвращается, только если указанная базовая версия больше не существует и требуется полная синхронизация.

Если конфликт появился уже после передачи содержимого в S3, завершение загрузки вернёт HTTP `201` и:

```json
{
  "conflict": true,
  "code": "FILE_VERSION_CONFLICT_COPY_CREATED",
  "file": {
    "id": "uuid",
    "name": "Документ (конфликт Сотрудник 2026-07-23 12-00-00 abc123).xlsx",
    "conflictOfFileId": "uuid",
    "conflictBaseVersionId": "uuid"
  }
}
```

Конфликтная копия является обычным самостоятельным файлом. Она не перезаписывает текущую серверную версию и синхронизируется через событие `upsert`. Если исходную папку удалили или доступ к ней отозвали во время загрузки, копия сохраняется в личной корневой папке сотрудника.
