# Ускорение после восстановления room 17

Проверено 2026-09-15 по исходникам `C:/Users/User/Desktop/Projects/MobileApp/mobile-app`. Данных устройства Ивана до очистки нет. Причинную связь с наблюдаемым ускорением нельзя считать измеренной.

## Что действительно очистилось

`services/ChatRecoverySettings.tsx:23–27`: очередь выбранного room текущего пользователя, кэш сообщений этого room, его черновик. Затем предложен полный перезапуск. Это четыре одновременно изменившихся фактора. Общие логи и кэши остальных чатов эта операция не удаляет.

## Подтверждённый источник лишней работы

- `services/outbox.ts:88`: очередь всех чатов хранится одним JSON в AsyncStorage (`app:outbox_v1`). Каждый loadOutbox заново читает и разбирает весь JSON. Ограничения очереди по количеству/байтам здесь нет.
- `services/outboxWorker.ts:578`: цикл проверяет только непустоту массива, обнуляет idle backoff и запускает выбор сообщения.
- `services/outboxWorker.ts:172` → `services/outbox.ts:191`: peekNext снова читает и разбирает весь массив. Failed-сообщения не выбираются, но остаются в массиве.
- При непустой очереди таймер остаётся 4 секунды. При пустой постепенно увеличивается до 20 секунд. Подписки на изменения очереди/сети/активацию приложения могут вызывать дополнительные проходы.
- Воркер принадлежит корневому layout (`app/_layout.tsx:286`), поэтому работа не ограничивается открытым room. Нельзя утверждать, что таймер работает во время приостановки JS операционной системой.
- Изменение статуса, добавление и удаление сообщения также читают/перезаписывают общий JSON. Большая проблемная запись увеличивает стоимость операций в других чатах.
- HTTP 413 уже считается неретраебельной ошибкой. Подтверждённая проблема — повторная локальная обработка сохранённого failed, а не бесконечная повторная HTTP-отправка этого failed.

## Воспроизведение

`test-outbox-idle.cjs` компилирует реальные outbox.ts/outboxWorker.ts через установленный в мобильном проекте TypeScript. AsyncStorage, сеть и React Native заменены заглушками. Записи исключительно искусственные, хранилища телефона/БД не затрагиваются. Внутренний цикл вызывается пять раз; реальные таймеры не ожидаются. Проверяется вычисленный интервал, а не длительность работы телефона.

## Другие возможные факторы

`services/messageCache.tsx:75` ограничивает room-кэш 30 сообщениями, но не байтами. Одно огромное сообщение всё ещё может быть тяжёлым. Проверка доверенных снимков отдельно ограничена 512 KiB оценочного размера на снимок и 8 MiB суммарно; это не ограничение сохранённого JSON. Большие снимки не попадают в этот быстрый путь. Кэш и черновик прежде всего объясняют проблемы открытия/работы конкретного чата. Перезапуск мог дополнительно освободить удерживаемую память.

Появление 30 новых сообщений не вытесняет failed из отдельной очереди отправки. Автоматически чистить очереди всех пользователей нельзя: там могут быть нужные неотправленные сообщения.

## Как проверить на устройстве

1. Добавить разовый диагностический снимок: размер очереди, количество по статусам и аккаунтам, длина максимального текста, размер room-кэша и черновика. Не собирать содержимое сообщений и токены.
2. Включаемые по умолчанию выключенные измерения на короткий сеанс: число проходов воркера, время чтения/parse/stringify/записи, задержки JS event loop и отклика интерфейса. Хранить агрегаты и ограниченный буфер, не бесконечный журнал.
3. На тестовом телефоне/аккаунте сравнить одинаковую сборку и сценарий: пустая очередь, одна большая failed, много небольших failed. Отдельно проверить тяжёлый кэш и черновик. Между сценариями одинаково перезапускать приложение. Не возвращать проблемные данные Ивану.
4. Сравнить p95/p99 задержек JS и время открытия/отправки. Если паузы совпадают с обработкой очереди и исчезают после исправления при сохранённых данных, причина подтверждена на устройстве.

## Порядок исправлений

1. Планировать обработку по наличию доступных к отправке сообщений текущего аккаунта, а не по длине очереди. Failed сохранять для ручного восстановления, но исключить из активного планирования. Убрать повторное чтение при выборе. Проверить retry deadlines, восстановление sending, reconnect, смену аккаунта и параллельную загрузку видео.
2. Убрать постоянное чтение большого JSON в простое: согласованный снимок с инвалидированием либо индекс метаданных. Простого замедления таймера недостаточно. Учесть записи фоновых загрузок, чтобы не создать потерю обновлений.
3. Проверять размер исходящего текста до сохранения в очередь, предлагать отправку файлом. Большие существующие failed не удалять молча. Отдельно рассмотреть хранение содержимого по записям, чтобы изменение одного статуса не переписывало все тексты.
4. Ввести бюджет байтов для восстанавливаемого с сервера кэша сообщений; не распространять вытеснение на единственную копию неотправленного текста.

На момент первоначального анализа код приложения не изменялся. Проверка доказывает механизм лишней работы, но не измеряет, насколько он тормозил конкретный телефон.

## Внедрение 2026-09-15

По согласованию внесены изменения в мобильный проект:

- Воркер один раз загружает очередь при запуске и сохраняет только метаданные планирования без текстов. Все изменения очереди обновляют эти метаданные через существующую подписку. Ревизия защищает первоначальное чтение от гонки с изменением очереди.
- Failed/sent не попадают в расписание; другой аккаунт не запускает отправку. Таймер в простое не читает AsyncStorage и не проверяет сеть. Ожидающие retry и sending сохраняют проверку сроков с интервалом 4 секунды; реальная отправка перечитывает актуальную очередь и сохраняет существующие проверки отмены/сессии.
- Новые тексты ограничены 16 000 единицами UTF-16 (эмодзи могут занимать две). Общий ChatInput проверяет длину до очистки текста, room дополнительно проверяет программный вызов отправки/редактирования, pushToOutbox защищает остальные пути постановки в очередь. Предлагается вручную прикрепить .txt; автоматической конвертации в файл нет.
- Новые снимки кэша ограничены консервативным бюджетом 256 KiB плюс прежним количеством. Сохраняется непрерывный хвост истории от самого нового сообщения, чтобы пагинация не пропускала вытесненные записи. Огромное самое новое сообщение может оставить офлайн-кэш пустым до обновления истории; оригинал на сервере и очередь не удаляются. Существующие снимки ограничиваются при чтении в память и заменяются ограниченными при следующей записи, массовой очистки хранилищ нет.

Тест теперь проверяет исправленное поведение и отказ слишком длинному тексту до доступа к хранилищу. Прошли также test-video-outbox.cjs, test-verified-message-cache.cjs, test-offline-chat-cache.cjs и новый test-message-cache-budget.cjs (бюджет, непрерывность истории, огромное последнее сообщение, неизменность исходных данных).

## Второй этап: отдельные записи и лимит 5 000

Добавлен `services/outboxStorage.ts`. Каждое сообщение хранится отдельной записью `app:outbox_v2:record:*`; индекс `app:outbox_v2:index` содержит только упорядоченные ключи. После первоначального чтения используется неизменяемый снимок в памяти. Обычное изменение сообщения записывает только новую версию этой записи и индекс. Неизменённые сообщения не читаются и не сериализуются повторно. Массивы для вызывающего кода отдельные; объекты сообщений заморожены, изменения выполняются заменой объекта.

Миграция `app:outbox_v1` автоматическая, без отсечения старых больших текстов или изменения их статусов. Сначала сохраняются отдельные записи, затем индекс. До успешного сохранения индекса старая очередь остаётся источником данных. После успешного переноса старый ключ удаляется. Наличие нового индекса, в том числе пустого, исключает повторное восстановление уже удалённых старых сообщений.

При обновлении используется copy-on-write: старая запись остаётся действительной до переключения индекса. Очистка неиспользуемых записей выполняется после успешного переключения; после аварийного завершения остатки удаляются при следующем успешном запуске после проверки индекса и чтения всех его записей. Ошибка чтения/разбора не подменяется пустой очередью. Напоминание о неотправленных сообщениях обрабатывает отказ чтения. Старый вспомогательный скрипт резервирования теперь читает очередь через общий API.

Отклонённый автоматической проверкой дополнительный шаг очистки перед повтором миграции не применялся; очистка остаётся после успешной проверки/фиксации нового состояния.

Лимит новых текстов снижен с 16 000 до **5 000 единиц UTF-16**. Проверка общего поля ввода и room использует общий валидатор; превышение не очищает поле. При переносе существующие длинные сообщения сохраняются без изменений.

Новый формат пока загружает все записи очереди в память при первом обращении. Отрисовка огромных входящих сообщений — отдельный вопрос, этот перенос её не меняет.
